# Приоритизация проблем и решений «Будущее 2.0»

## 1. Приоритизация проблем по MoSCoW

| Категория            | Проблема                                            | Обоснование (связь с целями бизнеса)                                                                                           |
|----------------------|-----------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------|
| Must have            | Монолитный DWH с бизнес-логикой                     | Блокирует запуск новых направлений (финтех, ИИ, партнёры). Критично для выручки и time-to-market.                              |
| Must have            | Долгое построение отчётности                        | Напрямую влияет на скорость управленческих решений и качество сервисов.                                                        |
| Must have            | Смешение медицинских и финансовых данных            | Регуляторные риски; без решения нельзя переезжать в облако.                                                                    |
| Must have            | Устаревшая СУБД SQL Server 2008                     | Без модернизации невозможна облачная миграция и масштабирование.                                                               |
| Should have          | Сильная связанность через ESB                       | Влияет на надёжность, но можно временно сохранить при поэтапной миграции.                                                      |
| Should have          | Легаси-интерфейс PowerBuilder                       | Снижает качество работы операторов, но не блокирует стратегию.                                                                 |
| Should have          | Отсутствие портала самообслуживания                 | Критично для финального состояния, но можно внедрить после доменного разделения.                                               |
| Could have           | BI-кастомизации                                     | Можно оптимизировать после перехода на новые домены.                                                                           |
| Could have           | Большое количество трансформаций                    | Решается по мере внедрения Data Mesh / Data Products.                                                                          |
| Won't have (сейчас)  | Аналитика по медицинским картам и историям болезней | Компания не планирует использовать эти данные для аналитики; фокус — на операционных сценариях.                                |

## 3. Приоритизация решений по матрице Эйзенхауэра

Ниже приведены **решения**, которые устраняют выявленные проблемы. Приоритет связан с целями бизнеса: выручка, time-to-market, качество медицинских и финансовых сервисов, соблюдение регуляторных требований.

| | Срочно | Не срочно |
|-|--------|-----------|
| Важно    | • Изоляция медицинских и финансовых данных — критично для compliance и переезда в облако.<br>• Пилот облачной миграции и Lakehouse — устраняет узкие места DWH и устаревшую СУБД.<br>• Замена ESB на Kafka + API Gateway — снижает связанность и повышает надёжность.<br>• Внедрение IAM и шифрования — обязательное требование регуляторов. | • Доменное разделение (DDD) — стратегическая основа для независимого развития.<br>• Data Mesh и Data Products — долгосрочная модель управления данными.<br>• Портал самообслуживания + DataHub + семантический слой — ускоряет принятие решений бизнесом.<br>• Модернизация интерфейса клиник (Web/Mobile) — повышает качество медицинских услуг.<br>• Подключение партнёров (фарма, электроника) — новые источники выручки.<br>• Observability и DR — обеспечивают надёжность и отказоустойчивость. |
| Не важно | • Временная поддержка PowerBuilder — до завершения миграции на новый интерфейс.<br>• Точечные доработки BI-кастомизаций — чтобы не останавливать текущую отчётность. | • Косметические улучшения легаси-систем — не влияют на стратегические цели.<br>• Рефакторинг старых ETL без бизнес-цели — можно отложить или исключить. |

### Связь решений с бизнес-целями

- **Выручка**: критичны решения по изоляции данных, доменному разделению, подключению партнёров и миграции Core Banking в облако.
- **Time-to-market**: ускоряют доменное разделение, Data Products, портал самообслуживания и замена ESB на Kafka.
- **Качество медицинских услуг**: повышают модернизация интерфейса клиник, ИИ-сервисы и изоляция медданных.
- **Качество финансовых услуг**: обеспечивают Core Banking в облаке, IAM, шифрование, DR и отказоустойчивость.
- **Соблюдение требований регуляторов**: обязательны изоляция медданных и финданных, IAM, шифрование, аудит и геораспределение.
